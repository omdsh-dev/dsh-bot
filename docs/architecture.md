# Architecture

[中文](architecture.zh.md) | English

Bot Mode is a Host/Client Cordis plugin loaded through a DSH profile patch in Web or Desktop. The Host owns identities, canonical direct chats, membership, routing, and public history in DSH's `bot_mode` storage domain. The Client contributes to the existing main panel and sidebar slots and uses generated Remote codecs. There is no separate chat server or SDK subprocess.

Each Bot has a persistent native Session per chat membership. Scoped system-prompt contributions supply its identity. A delivery records bounded unseen public messages, an optional reply quote, and the current human request; private chat transcripts are not copied into group context. Explicit mentions take precedence over reply routing and the default responder. Human sends and retries dispatch model work. Compatible IM connectors additionally admit bounded handoffs inside one external group: a completed reply reserves child attempts atomically, with the human root ID and concrete task. Each Bot receives at most three task assignments per human root, with twelve total handoffs and task deduplication; a child never crosses Rooms or providers. The connector retains ownership of its response tree, queues completed replies progressively, and sends each through the corresponding robot. Robot-originated platform events are still ignored.

The public transcript and native Session log are separate durable stores. An interrupted process can leave the public response marked interrupted after its underlying Turn completed. Startup does not replay uncertain work. Durable task joins may resume the parent with completed or interrupted child results. A callback is reserved with child settlement to prevent duplicate summaries. Stop cancels the owned response, and unloading the plugin cancels and drains its active work. Removing and rejoining a member creates a new Session without deleting public history.

Long-term memory uses immutable `bot_memory_*` chunks referenced by the atomic `bot_mode` manifest but is excluded from ordinary snapshots. Dedicated operator APIs manage global, Bot, group and user records. Conversation tools can only propose pending records with immutable source scope. Retrieval filters identity and access before relevance, applies preference precedence, preserves conflicting facts, and records bounded memory frames in native Session input. Idle conversation reviews create evidence-backed candidates through a bounded durable retry queue. Explicit account links preserve source-room access rules. Conversation search, memory recall, task status and structured delegation are scoped tools. Request-boundary context rotation creates structured handoffs; forgetting invalidates old Sessions. See [memory](memory.md) for the identity model, costs, cancellation and retention limits.

This repository keeps the plugin source and a small integration patch. The patch adds workspace TypeScript paths, compiler references, and the plugin's pnpm lockfile importer. It does not modify the Agent loop, runtime transport, authentication, or model providers. Setup uses a pinned upstream checkout so generated APIs and native slots have a reproducible owner. Upstream generated documentation catalogs are not needed for this opt-in runtime.

The source distribution prepares a pinned DSH checkout for building. `npm run pack` wraps the compiled implementation in the public `@zzzpyyy/dsh-bot` bundle, whose `dsh.bundle.patch` activates the nested entry. The implementation keeps its original private package identity because generated Typert codecs and client module registration refer to that identity. No generated identifiers are rewritten. The outer manifest converts host-owned dependencies to the ranges in `compatibility.json` and keeps ordinary dependencies separate; source files, tests, build helpers, and `workspace:` ranges are excluded.

Desktop discovers the same `dsh.client.platform: web` entry as the browser interface. On DSH 0.2.0, Desktop starts the native Web Host and connects using its authenticated HTTP URL. The plugin contains no Desktop-specific server or transport. Desktop manages its own profile and data. For the source Web launcher, `.runtime/` is rebuildable and `.data/` holds user state that must be retained across updates. Native tools and model credentials remain DSH's responsibility.

See the [plugin reference](plugin-reference.md) for configuration, model-visible effects, and deferred features. The profile test launches built DSH twice with only the external model replaced and checks identity isolation, group/private context, cancellation, feed ordering, and persistence.

Archive tests unpack the shipped tarball, use DSH's actual profile compatibility gate, and launch the native Desktop Host without version exemptions. Only the external model is replaced. Tests authenticate to the Host, fetch the registered Bot client module, restart the Host, and verify stable Session IDs. The same archive is also loaded through the Web CLI. The test resource tree is not a signed app bundle; macOS window interaction is a separate manual check. `npm run test:install` uses the shared plugin manager to install local base and Feishu archives into a fresh profile before starting Desktop. The opt-in `npm run test:registry` repeats this against published versions on npm.

The archive fixture uses Desktop's own dependency-closure selector to limit shared packages, so development-only packages cannot mask missing dependencies. The declaration-only `dsh-client-ui-slots` dependency remains in the source workspace for type checking and is omitted from the bundle's runtime peers.

The optional InfoFlow companion calls Host-only BotMode methods and exposes a narrow manager interface through BotMode Remote methods. The manager owns versioned `bot_infoflow_settings` and independent `bot_if_*` inbox/outbox domains per Bot or managed group; legacy mode retains `bot_infoflow`. Multiple robot deliveries share one group receipt and separate Bot Sessions. External room identities and message receipts live in bot_mode, committed atomically with response attempts. Network delivery never holds the admission lock. See the [InfoFlow guide](infoflow.md).

The optional Feishu manager owns per-Bot app credentials and independent `bot_fs_*` queues. Its durable group requests create private platform groups, invite selected apps and enable their group allowlists. Retries reuse the saved remote ID or bounded API UUID. Each Feishu group has one external Room keyed by chat ID, with a separate native Session per Bot; DMs remain app-scoped. BotMode atomically deduplicates a shared human message and admits each mentioned Bot once. Legacy rooms merge with retained IDs as aliases for queued replies. See the [Feishu guide](feishu.zh.md).

Compatibility policy and build provenance are separate: the build stays pinned while all three npm archives accept later DSH versions. Plugin-owned icons remove an unstable UI export dependency; Host, Agent, Client and IM entry points check required methods before use. See [compatibility](compatibility.md) for verified revisions, limitations and the same-artifact test matrix.
