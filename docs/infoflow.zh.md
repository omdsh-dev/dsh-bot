# 如流文本接入

本功能属于 DSH Bot 0.7.0，配套插件为 `@zzzpyyy/dsh-bot-infoflow@0.4.0`，最低要求 DSH `0.1.5-rc.2`，同一安装包已验证 `0.1.5-rc.2` 和 `0.2.0-rc.2`；后续版本按[兼容策略](compatibility.md)检查接口。如流插件作为同一 Host 的可选 Cordis 插件运行；基础 Bot 包不依赖如流 SDK。安装配套包不会自动连接机器人，必须先配置并启用。

## 能力与会话

每个 DSH Bot 可绑定一个独立的如流机器人，分别保存凭据、准入名单和连接开关；同一个如流机器人不能绑定多个 Bot。从 **DSH Bots → IM 接入 → 如流** 打开配置。配置页提供三步创建指引、整段凭据粘贴、保存并连接、测试消息、连接状态和启停操作。基础 Bot 包不安装 SDK 也能使用本地聊天。

同一个 DSH Bot 可以同时绑定并启用如流和飞书机器人。两边的凭据、准入名单、连接开关独立；在一个平台停用连接不会停用另一个平台。Web、飞书、如流的私聊和群聊分别保存消息和模型对话上下文，回复只返回发起请求的平台及聊天，不自动跨平台转发或合并同名群。Bot 指令、模型和工具配置共用；文件、外部服务及工具主动写入的记忆由部署配置控制，不随聊天自动隔离。飞书配置见[飞书接入指南](feishu.zh.md)。

支持文字私聊和群内 @机器人、发送者身份、持久化排队、重复消息去重、结果分片回发、失败重试及原生人工处理提醒。每个 Bot 的如流私聊与既有本地私聊分别拥有独立 Room 和 Session。通过页面创建的如流群使用一个共享 Room，各 Bot 保有独立 Session；同一条消息投递到多个机器人时，只进入一次共享历史，每个被 @ 的 Bot 通过自己的机器人回复。

页面绑定的机器人直接发送回复正文，不额外添加 `@botId` 行；发送者名称和头像标明回复身份。模型正文中的正常 @ 文本原样保留。旧式单连接若通过同一个如流机器人调用多个 Bot，仍保留文字身份标记。

必须匹配平台 AT 块中的 `robotid`；仅显示名、@所有人、其他机器人的 AT 和全量群转发事件均不触发。当前仅接收 `private.text`、`private.markdown`、`group.text`、`group.markdown`、`group.mixed` 中的文字/Markdown/链接；图片、附件和引用块不进入模型，图片单独消息不处理。适配层保存字符串 ID；SDK 内部对群 ID 的数字转换仍受其实现限制，超大群 ID 尚未在真实平台验证。

外部 Room 在 DSH 界面中显示来源和发送者，只能查看、停止响应和打开执行会话。发消息请回到如流。连接器不接受本地 `send`、成员编辑或一键重试，避免意外向外发布消息或重跑不确定的工具操作。

## 构建和安装

已有匹配版本 DSH CLI 时，先配置组织授权的 `@baidu` registry，再将以下包安装到当前服务使用的 Web profile：

```sh
dsh plugin --profile web add @zzzpyyy/dsh-bot@0.7.0
dsh plugin --profile web add @zzzpyyy/dsh-bot-infoflow@0.4.0
```

Desktop 可在插件管理器中按相同顺序安装这两个精确版本，同样需要能解析企业 SDK 依赖。包使用 `next` 标签；安装时建议指定版本。

准备好源码工作区后运行：

```sh
npm run build:plugin
npm run pack
npm run pack:infoflow
```

首次安装源码仍使用 `npm run setup`。上述增量构建要求工作区及依赖已安装，会重新生成 Remote 编解码器。产物分别是 `dist/zzzpyyy-dsh-bot-0.7.0.tgz` 和 `dist/zzzpyyy-dsh-bot-infoflow-0.4.0.tgz`。

对于已有匹配版本 DSH CLI 的 Web profile，可从本仓库目录执行以下命令；使用你实际的 `DSH_HOME`，并先配置好组织授权的 SDK registry：

```sh
dsh plugin --profile web add ./dist/zzzpyyy-dsh-bot-0.7.0.tgz
dsh plugin --profile web add ./dist/zzzpyyy-dsh-bot-infoflow-0.4.0.tgz
```

配套包依赖企业 SDK `@baidu/infoflow-sdk-nodejs@2026.8.28`。在目标 profile 的包管理环境中配置组织授权的 `@baidu` registry；仓库和公共配套包不携带私有 registry、令牌或 SDK。CLI 的 `dsh plugin add` 支持 tarball，安装到同一 profile 时先安装基础包，再安装配套包。请使用与目标 profile 相同的 `DSH_HOME`。Desktop 插件管理器只接受 registry 包，不能直接安装本地 tarball。

源码开发时也可在独立目录安装 SDK，并将编译后的 `lib/infoflow.js` 复制到该目录，使用 DSH `--patch` 挂载该文件；此目录还必须能够解析配套包声明的DSH peer 范围 和 zod。推荐使用上述配套包方式，避免污染托管 `.runtime` 的冻结锁文件。

## 页面配置

开发版（尚未发布到 npm）对新用户默认隐藏如流入口和建群选项。先在 **DSH Bots → IM 接入 → 高级设置** 打开 **显示如流接入（内部用户）**。设置保存在当前 DSH profile，刷新、重启及同一 profile 的其他客户端保持一致。已有如流绑定、建群记录或聊天记录时升级保留入口；显式关闭后不会因旧记录重新打开。关闭显示不停止已有连接、不删除凭据或聊天；要停用机器人，请操作该机器人的“停用连接”。这只是显示设置，不是内部身份认证或权限控制。

配套包默认启用管理页面（`managed: true`），但不自动连接任何机器人。在 **DSH Bots → IM 接入 → 如流** 中：

1. 在[如流开放平台](https://open-ruliu.baidu-int.com/web)新建应用，在「凭证与能力」复制 App ID、App Key、App Secret；在「可见范围」配置使用者和目标群。
2. 选中 DSH Bot，把「复制全部」内容粘贴到专用输入框，或手动填写 AppKey、AppSecret。应用 ID 可留空自动获取；填写时会核对是否属于同一机器人。粘贴支持带标签文本和 JSON，仅在浏览器本地识别，不会自动保存或发消息。
3. 填写允许私聊的账号。已有群可以填写群号，或显式勾选「允许机器人所在的所有群 @ 调用」。账号支持邮箱前缀或完整百度邮箱，多个值用逗号分隔。停止任务管理员位于高级设置。
4. 点击「保存并连接」验证身份、保存并启动连接，查看连接状态；也可仅「验证并保存」。已有绑定的仅保存操作保留原来的启停状态。重置未保存修改不会删除绑定或停用连接。
5. 从已保存的私聊账号中选择测试接收者，点击「发送测试消息」。收到后，在如流回复“连接测试”，验证接收和回答。测试按钮只发固定诊断文本，不调用模型、不自动启用连接，也不会自动重发；平台确认发送不代表接收链路已验证。

凭据写入 DSH 原生凭据提供方，普通设置只存引用名；页面不读回或显示已保存的密钥。编辑时密钥留空表示保留原值。一个机器人如果仍由其他进程接收回调，先停用旧接收服务，再启用此连接；SDK 的长连接注册可能改变机器人回调方式。

`allowUsers` 控制私聊；`allowGroups` 控制手工添加的已有群，允许群内的成员可 @机器人执行任务。`allowAllGroups` 默认关闭；显式打开后，机器人所在且平台允许的群中所有成员均可 @ 它调用对应 Bot，私聊名单不变。升级保留原来的准入范围。`admins` 赋予已允许会话中的停止权限，不自动放开准入。已有群由每个 Bot 单独接入；多 Bot 共用一个历史的模式由下述建群流程建立。

遇到 `40070`，请检查接收者是否在应用可见范围内、是否已关注机器人。平台可见范围和 DSH 准入名单同时生效；只改其中一处可能仍无法使用。测试错误不会回传 SDK 原始响应或密钥。

## 可选创建如流群

在 DSH 的“创建群聊”窗口中，**“同时创建如流群聊”默认不勾选**。勾选后填写群主账号和其他人类成员，再选 Bot 和默认 Bot。所选 Bot 都须已绑定并启用如流机器人。

提交后，系统使用默认 Bot 的机器人凭据调用 SDK 建群接口，邀请所选 Bot 的机器人，并建立对应的 DSH 外部 Room。群主可以停止该共享会话的任务。账号还需要平台允许的建群和邀请机器人权限。若部分成员邀请失败，页面保留群 ID 并显示失败成员，去如流补充处理即可。

创建流程先持久化请求，再调用平台；拿到群 ID 后先保存它，再关联本地 Room。重复提交同一请求不会再次建群。若只缺本地关联，可在“IM 接入 → 如流”页点击“恢复关联”；若网络超时导致平台是否建成未知，则显示“结果未确认”，系统不会自动重复建群，请先到如流确认。当前没有按未知结果自动找群或手填群 ID 恢复的功能。

## 兼容旧配置

一个 Host 安装一个管理器，由管理器维护多个机器人。原单机器人模式仍可使用 `managed: false`；此模式不通过新页面管理。旧配置加 `managed: true` 后，可将 `defaultBot` 对应的机器人导入为一个**停用的绑定**，其余 Bot 在页面分别配置。导入不搬迁旧连接器的在途队列或已建立外部 Room，应先处理完旧队列再切换模式。

旧模式配置示例：

```yaml
- id: bot-infoflow
  disabled: false
  config:
    managed: false
    accountId: "YOUR_AGENT_ID"
    robotId: "YOUR_GROUP_AT_ROBOT_ID"
    appKeyRef: INFOFLOW_APP_KEY
    appSecretRef: INFOFLOW_APP_SECRET
    botIds: [architect, critic]
    defaultBot: architect
    allowUsers: [YOUR_USERNAME]
    allowGroups: []
    admins: [YOUR_USERNAME]
```

`accountId` 是 Agent ID，不是 AppKey；`robotId` 是 `client.robot.getInfo().imId`。旧模式私聊用 `defaultBot`，群内文本 `@handle` / `@all` 在 `botIds` 内路由；新模式以实际被 @ 的如流机器人选择 Bot。已有 Room 的 Bot 列表与默认 Bot保持固定。

## 高级部署设置

| 配置 | 默认值 | 作用 |
|---|---|---|
| `maxPending` | 200 | 待执行和执行中请求总上限 |
| `maxQueuePerRoom` | 20 | 每个外部会话待处理请求上限 |
| `maxConcurrentRooms` | 4 | 同时执行的外部 Room 数量 |
| `maxReceipts` | 100000 | 保留的入站去重凭据上限，满后拒绝新接收，需部署者扩容 |
| `maxOutbox` | 10000 | 待回发消息分片上限 |
| `chunkSize` | 3000 | 每个分片的 Unicode 码点数量，最大 3000 |
| `retryMs` / `maxRetryMs` | 5000 / 120000 | 回发失败的指数退避范围 |
| `connectRetryMs` / `maxConnectRetryMs` | 5000 / 120000 | 首次连接失败的退避范围；已连接后的重连交给 SDK |
| `endpointTimeoutMs` / `sendTimeoutMs` | 30000 / 30000 | 端点请求超时与发送确认等待上限 |
| `pollMs` | 1000 | 状态对账与失败投递检查间隔 |
| `baseUrl` | 空 | 留空使用 SDK 默认值；覆盖值必须为 HTTPS URL |
| `wsGateway` / `wsConnectDomain` | 空 | 留空使用 SDK 默认值；覆盖值为域名，不包含协议或路径 |

首版使用 SDK 的直接连接，不修改全局 HTTP 代理，也不自动打私有 SDK 传输补丁。需要代理的部署应先确认企业 SDK 的正式代理能力；本版本未验证代理网络。SDK 版本检查失败会阻止启用，不会悄悄切换协议版本。

## 指令与审批

`/help` 显示用法；`/bots` 显示配置的 Bot；`/status` 显示当前会话排队与执行数量；`/stop` 取消自己在该会话中排队和执行的请求，管理员可停止该会话全部请求。停止指令在接收时绑定具体响应 ID，重复投递不会误停后来的任务。群内指令同样需要 @当前机器人。

审批和提问继续由原生 DSH 处理。连接器只发送“请部署者打开执行会话”的提醒，不提供批准接口、不变更权限 preset，不发送认证链接或原生工具细节。没有可用答复处理器时，仍按 DSH 的原有机制返回不可用结果。会话隔离只隔离聊天历史；工具运行目录、文件访问权限、模型和凭据仍由此 DSH 部署及其 preset 决定。

## 持久化与恢复语义

页面管理模式将配置和建群记录保存在 `bot_infoflow_settings`，每个 Bot 和共享群的收发队列使用独立 `bot_if_*` 域；旧模式保留 `bot_infoflow`。入站接收凭据与待处理内容一起写入对应队列域后，才排入“已接收”回执。Room 忙碌时排队。BotMode 在一次 `bot_mode` 提交中写入原平台消息 ID、人类消息及全部响应尝试，然后启动执行。相同平台消息 ID 重投会返回原响应 ID；连接器在 Bot 提交后丢失状态写入，也不会再次执行。

最终结果与不可变的收件会话写入持久化回发队列。每个分片在平台返回成功后才移除，失败按退避重试，并保持同一会话的分片顺序。超时不能证明平台没有收到消息，重试可能产生重复回复；不会因此重复调用模型。SDK 对进程离线期间的补投与确认语义需用企业账号验证；这里的持久化保证始于连接器成功写入输入，并不承诺平台到 Host 的端到端 exactly-once。

进程崩溃后，原来 `running` 的公开响应变为 `interrupted`，如流收到中断说明；不会自动重跑不确定的工具执行。正常卸载连接器保留请求和回发队列，不取消 BotMode 拥有的执行。修改账号 ID 后旧账号消息保留，恢复原账号配置后才能继续投递，不会转投新账号。

`bot_mode` 保持后端 v1，使用可选 `external` 字段做向后兼容读取。旧数据中的 Bot、Room 和 Session ID 都保持原值。已有数据不支持退回会丢弃未知字段的旧版 Bot 插件；部署升级前备份整个 DSH 数据目录。历史条数仍受 BotMode `maxMessages` 限制，满后给出明确提示。

## 验证范围

仓库测试使用确定性模型和模拟如流传输，覆盖页面表单、独立机器人绑定、可选建群、建群超时恢复、共享群双机器人回复、消息解析、私聊隔离、群内多 Bot、去重、排队、停止权限、写盘失败、发送失败、SDK 调用格式、连接重试、发送超时、原生 DSH 强制退出后的恢复，以及 Web/Desktop 基础包加载。它们不要求真实机器人凭据，也不向如流发送消息。企业 SDK 安装、真实账号的接收事件、网关可达性和实际发送权限需要部署时联调。
