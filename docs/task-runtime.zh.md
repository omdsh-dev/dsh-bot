# 任务运行底座与恢复边界

本轮在原有多 Bot / 多房间交互上增加任务层，不增加一个对外 Router，也不把 Bot 会话替换为另一套执行引擎。代码借鉴持续 Agent 架构中的任务身份、状态与执行分离、独立控制入口和不确定结果恢复。

## 已落地

### 任务、执行与事件

- **Task**：一次已接收的用户请求，ID 沿用根用户消息 ID。
- **Run**：该任务的一次 Bot 回复执行，ID 沿用回复 ID；保留父执行、自动回调、显式重试和原生 Session 引用。
- **Event**：创建、执行状态、任务状态、取消意图和人工验收的元数据。任务账本与消息在同一状态事务提交，在聊天历史分片前更新；流式 token 不生成事件。
- 多 Bot 委派、Session 压缩/接续、显式重试保持任务关联。任务不是一个新房间，暂不把跨渠道、跨房间的请求自动合并。
- 原生 `turn/end completed` 仅表示执行结束。全部相关执行结束且无失败时进入 `awaiting_verification`；用户检查产物并验收才成为 `verified`，新执行会使旧验收失效。失败子任务不会因父 Bot 给出总结而被自动视作成功。

每条 Bot 回复的「**任务与恢复**」可以查询执行和生命周期记录。查询直接读取已提交元数据，不占用模型调用、不排在聊天执行之后。展开时读取，也可以手动刷新。

### 明确的请求级权限

输入框增加「**本次请求权限**」：

- 继承 Bot / 部署权限（默认，行为不扩大）；
- 禁用工具；
- 原生文件 / Shell 只读。

结构化 API 也支持精确工具白名单：

```ts
await remote.bots.send({
  roomId,
  text: '检查并总结，不修改文件',
  taskPolicy: { fileMode: 'read-only', toolMode: 'allow', tools: ['read_file', 'search_chat', 'read_chat', 'task_status'] },
})
```

工具名必须使用当前部署的实际完整名称；示例不是默认授权列表。策略只做收窄，不能授予部署或 Bot 本来没有的权限。宿主验证策略并保存独立副本；每次执行从原用户请求读取，与目标 Bot 策略取交集，子 Bot 不能在委派文本中覆盖它。问答、表单接续以及已确认邀请所共享任务的策略会继续传递；新用户请求仍是新的授权边界，不从普通引用自动推断授权。

“只分析，不修改”等自然语言仍是模型指令，**不会自动转换成安全策略**；需要选择上述选项或显式传入 `taskPolicy`。文件模式通过原生沙箱实施，另在直接工具分发（包括 PTC 嵌套分发）校验提权参数，并在 Session 被放宽时中止受限任务。缺少必要执行能力会拒绝执行，不静默降级。

**重要限制：**

- 文件只读不是网络只读：MCP、浏览器或外部服务的写操作仍需精确工具授权控制。
- 策略/操作记录覆盖本项目调度的 Bot Run 的直接工具分发及 PTC 嵌套调用。原生 subagent 是独立 Agent，其工具白名单和操作记录尚未贯通；in-process subagent 虽有原生沙箱继承，不能据此声称继承了本项目全部策略；Codex/ACP 等外部执行器还可能使用自己的部署权限。
- 严格约束场景应禁用工具，或只允许已审核的直接工具，不允许开启另一个自主执行循环的工具。不能把工具名白名单当作其内部所有行为的完整安全证明。
- 仍依赖原生文件/命令沙箱后端；这不是跨进程、跨执行器的通用不可绕过沙箱。

### 工具操作先记账，再分发

每次进入实际 `tools/execute`：

1. 持久化 `{roomId, messageId, callId, name, startedAt}`，形成 `started` 意图。
2. **提交成功之后**才调用工具。写盘失败不执行；相同操作 ID 不重复派发。
3. 收到正常返回后记录 `returned`。它只表示收到返回，不保证 PR、CI 或其他业务目标已完成。
4. 异常、取消、未知副作用错误或回执无法可靠保存时，保留/标记为 `unknown`。进程重启将未完成的 `started` 转成 `unknown`，不重放工具。

账本不保存工具参数、返回正文、异常文本或凭据。原有聊天和原生 Session 的工具详情仍按其既有规则保存，并非被此账本替代。

对于本项目自己注册的聊天检索、记忆检索、任务状态和原子委派记录工具，已知本地动作失败允许模型纠正，不误报为外部结果未知。证据来自该宿主工具实现的单次调用标记，不按工具名称豁免；同名外部工具不能借用豁免。其他工具错误暂按保守策略处理，未来可以逐项增加可证明的失败/幂等语义。

出现未知结果时，关闭该根任务的自动委派/回调，取消排队分支并中止活动分支。**核对本身不续跑、不调用模型、不发起工具操作。**操作真正退出前不能人工核对；超时/取消后仍未退出的工具保留其限制，不提前恢复较宽沙箱。新的排队工作也等待原生 Session 释放。

恢复流程：

1. 打开原生 Session，并在对应外部系统核对实际状态。
2. 在「任务与恢复 → 工具操作凭据」勾选已检查，明确记录“已生效”或“未生效”。这是用户核对结果，不是系统自动验证。
3. 确实需要继续时，显式重试可重试的失败回复，或发送新的用户请求。已完成的派活者没有自动恢复入口；不能重试的外部请求按原规则仍需检查后重新发起。
4. 已生效的动作不应重做。重试输入提供此前操作引用作为依据，但它**不是远端 exactly-once 协议**：新 call ID 仍可能发起重复业务操作，需要操作适配器的幂等键、查询和结果复用进一步兜底。

### 查询、停止与验收控制

新增管理 API：

- `tasks({roomId, limit?})`：最近任务（最多 256）。
- `taskView({roomId, messageId})`：这条回复对应任务及工具操作元数据。
- `stopTask({roomId, taskId})`：先撤销执行并保存取消意图，返回后无需等慢工具完全结束。运行中的工具可能仍在退出，界面不会把“提交停止请求”称为外部操作已撤销。
- `verifyTask({roomId, taskId, outcome: 'accepted' | 'rejected'})`：人工验收，无自动测试/验收器。
- `resolveTaskOperation({roomId, messageId, callId, resolution})`：核对未知操作；`resolution` 为 `verified_applied` 或 `verified_not_applied`。决定不可覆盖；不会授予新权限。

这些接口沿用本项目的管理端授权边界，按房间/显式 alias 查找任务，Bot 的 `task_status` 仅返回当前人类请求，不提供全局任务读权限。普通 snapshot/feed 不携带整份任务/操作账本。

`localOnly` /「仅 DSH」沿用原有**投递范围**语义：不直接发送到 IM 平台，不是上下文保密边界。同房间共享的原生 Session 及后续模型输入仍可能包含这些内容。需要保密的信息应放入独立房间/Session，不应依赖这一标记隔离。

## 存储、升级与容量

- 采用 `bot_mode` 域的向后兼容可选字段，不删除旧消息、不自动重放旧任务。增量观察当前已加载消息和活动任务，不承诺回填全部历史归档。
- 每任务保留最多 256 个生命周期事件，并记录裁剪数量和单调序号。
- 每房间保留最近 256 个已结束任务摘要；活动任务、有未核对操作的任务不为满足这个上限而丢弃。保留 fence 防止历史加载后反复重建已裁剪摘要。
- 单次 Run 最多 512 条工具操作记录，整个 profile 最多 50,000 条。目前没有操作账本自动归档：到上限会在实际工具调用前拒绝继续，**不会删掉旧回执来掩盖容量问题**。长期运行前需要补归档和运维容量管理。
- 回执与任务状态使用原有原子主域事务，备份时与聊天、原生 Session 一起保留。存在未核对的操作时拒绝删除关联聊天/Bot，也拒绝从相关聊天移除成员，避免脱离恢复引用。原生工具仍在运行或退出时，不能通过移除再加入 Bot 换用新 Session 绕过退出等待。

## 仍未实现

这轮是第一阶段底座，不是完整 Super-agent：

- 任意前台自然语言与后台任务同时交互；目前分离的是状态/停止/核对控制入口，普通同房间消息仍按原规则排队。
- 主动 PR/CI/邮件等事件源、语义过滤和通用可重放事件队列。
- 独立语义 Watchdog、业务验收器、自动外部结果查询/对账。
- 每任务 worktree / 工作目录隔离、根任务全树预算与总时限。
- 原生 subagent/外部执行器完整策略继承、远端业务操作幂等协议。
- 跨渠道 Task/Thread 授权关联、操作账本归档和列表游标分页。

验证采用受控本地模型/工具、失败注入、原生 profile 构建与重启测试；不代表已对生产外部服务执行或验证了真实副作用。 详细过程与边界见[本次验证记录](task-runtime-verification.zh.md)。
