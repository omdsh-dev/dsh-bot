# Feishu per-Bot provisioning and text transport

A separate optional companion owns registration jobs, connections and the versioned `bot_feishu_settings` domain. Bot Mode exposes a narrow attach/detach configuration seam over generated Remote codecs. The public boundary types are exported at `./feishu/types`; source imports do not pull the optional SDK into the base Host or browser.

Use the public pinned SDK `registerApp` flow with `createOnly: true`; each remote app requires the user's QR confirmation. Do not substitute an internal registration endpoint or treat app creation as a retryable network operation. Registration results are written to DSH credentials before identity verification; new bindings stay disabled. Transient authorization links and QR data never enter native settings. Incomplete durable attempts become interrupted on startup. Canceling local authorization does not delete an already approved app.

One app binds to one Bot. Feishu Open IDs are app-scoped and must not be shared across bindings. Human text events require per-binding user/group allowlists; group messages must mention the current bot. Feishu group provisioning is owned by the [durable group creation decision](2026-10-15-feishu-groups.md). Shared group histories and legacy migration are owned by the [shared group decision](2026-10-15-feishu-shared-groups.md); private chats remain app-scoped. Original InfoFlow management and group creation remain separate and unchanged.

The transport shares the existing durable bridge, parameterized by provider, with a separate domain per Bot/app. It owns WS disposal and drains admitted handlers. SDK HTTP requests (including token and registration requests) have a configured timeout; SDK logs are contained to avoid credential-bearing upstream payloads. Sending retains a stable UUID but the provider's deduplication window remains finite.

Validation: source manager/SDK/UI cases and a real packaged native Host fixture with two apps, InfoFlow coexistence, duplicate ingress, blocked user/group messages, independent Sessions and restart replay protection. Tests use an offline SDK and do not create external applications or send external messages.

The four-entry acceptance fixture invokes the same Bot through Web DM, Web group @mention, Feishu DM and Feishu group @mention. It checks the effective identity and tool preset, original reply destination, independent Session/history, rejected and duplicate ingress, and restart stability. Enabling a connection does not widen group access: each target chat must be explicitly allowed for each binding.

Official EventDispatcher callback objects contain enumerable symbol metadata (`Symbol('event-type')`). Decode their string-keyed fields with an object schema; a string-keyed Zod record rejects that symbol and silently discards every incoming event. Transport regression tests and the packaged fixture include this metadata. An offline replay through the installed official 1.75.0 dispatcher reproduced the dropped DM before the fix and reaches ingress after the fix.

Set `DSH_FEISHU_SDK_FILE` to the installed official SDK module when running `node --test scripts/feishu-package.test.mjs` to exercise its real EventDispatcher through all four entry points. Only the external registration, socket and HTTP calls remain simulated; this check needs no credentials and sends no external messages.
